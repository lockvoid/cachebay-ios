# Architecture

A reference for *why* Cachebay-iOS is shaped the way it is, what it actually does on the hot path, and how it compares to Apollo iOS 2.x at the implementation level. Read [KEYNOTES](./KEYNOTES.md) first for the mental model; this doc is the deeper read.

Sources cited as `file:line`. Apollo paths refer to `apollo-ios` 2.x release sources.

---

## 1) Subsystems

Cachebay is six cooperating subsystems behind one client. Each owns its state and its lock:

| Subsystem      | File                                  | Owns                                                       |
| -------------- | ------------------------------------- | ---------------------------------------------------------- |
| `Graph`        | `Sources/Cachebay/Runtime/Graph.swift`     | The normalized record store. The truth.                    |
| `Documents`    | `Sources/Cachebay/Runtime/Documents.swift` | Materialize: plan + variables + rootId → typed `Data`.     |
| `Queries`      | `Sources/Cachebay/Runtime/Queries.swift`   | Query watchers + dep index.                                |
| `Fragments`    | `Sources/Cachebay/Runtime/Fragments.swift` | Fragment watchers + dep index.                             |
| `Optimistic`   | `Sources/Cachebay/Runtime/Optimistic.swift`| Layered, reconstructive optimistic mutations.              |
| `Operations`   | `Sources/Cachebay/Runtime/Operations.swift`| `executeQuery / executeMutation / executeSubscription`.    |

`CachebayClient` (`Sources/Cachebay/CachebayClient.swift`) wires them together. Construction order matters because the graph's `onChange` is a closure that calls into `Queries` and `Fragments`.

### Lock topology

Six `NSRecursiveLock`s with an enforced acquisition order:

```
Queries · Fragments · Optimistic · Operations
                  │
                  ▼
             Documents
                  │
                  ▼
                Graph
```

Cited as design intent in `CachebayClient.swift:38–41`. Each subsystem may take its own lock; if it then needs a *lower* one, that's allowed; never the other way around. Recursive because legitimate re-entry happens (a watcher's materialize calls `graph.getRecord`, which takes the graph lock again).

### The single most important rule

**Callbacks fire outside the lock.** `Graph.flush()` extracts the touched set under its lock, releases, and *then* invokes `onChange`. Watcher fanout, storage writes, and user callbacks happen with no graph lock held. This is the load-bearing perf decision; everything else is detail.

## 2) Hot path: mutation → graph → fanout → materialize

```
executeMutation(plan, vars)
        │
        ▼
  HTTP transport ─── network ───┐
                                ▼
                     parse response → JSONValue
                                │
                                ▼
                   Operations.merge(rootId="@mutation.N", data)
                                │
                                ▼
                   Documents.normalize(plan, data, rootId)
                                │            │
                                │            ▼
                                │    Graph.putRecord(id, fields)
                                │    [Graph.lock held briefly per record]
                                │
                                ▼
                   Graph.flush()
                     ├── lock.lock()
                     ├── pending = drainPendingLocked()
                     ├── lock.unlock()           ← lock released
                     └── onChange?(pending)       ← fanout, lock-free
                                │
              ┌─────────────────┼─────────────────┐
              ▼                 ▼                 ▼
   Queries.notifyDataBy   Fragments.notifyData  SQLiteStorage.put(..)
   Dependencies(touched)  ByDependencies(..)    [enqueued, returns]
```

The "lock released → fanout runs" boundary in `Graph.flush()` is the difference. Apollo holds the equivalent lock through fanout (§4 below).

## 3) Materialize: pre-baked plans + fingerprint cache

A `CachePlan` is a flat literal generated by `cachebay-cli`:

```swift
public static let cachePlan: CachePlan = CachePlan.make(
    operation: .query,
    rootTypename: "Query",
    root: [
        PlanField.make(responseKey: "project", fieldName: "project", ...),
        ...
    ],
    networkQuery: networkQuery,
    ...
)
```

Runtime never parses GraphQL. `Documents.materialize(plan, variables, options)` walks the plan against the graph, chasing `__ref` pointers, and returns a `JSONValue` tree (or, via codegen, typed `Data`).

A parallel **fingerprint tree** is computed alongside the materialised data. When a watcher refires, materialize keys cached results by `(plan id, variables canonical form, rootId)`. If the same selection over the same records produces the same fingerprint, the result is reused — including reused sub-objects so SwiftUI / Combine can identity-compare.

This is the second perf win after lock-released-before-fanout: **idempotent change → no work**.

## 4) Apollo iOS 2.x — head-to-head

Both clients solve the same problem the same way at a high level: parse → normalize into records keyed by `Type:id` → publish into a store → notify watchers → re-execute against the cache → callback. The differences live in *when locks are released*, *what watchers do on refire*, and *how SQLite participates*.

### 4.1 Lock ownership

| | Apollo | Cachebay |
|-|--------|----------|
| Type | `AsyncReadWriteLock` actor (`AsyncReadWriteLock.swift:1–133`) | Six `NSRecursiveLock`s |
| Granularity | One global lock per `ApolloStore` (`ApolloStore.swift:31`) | Per-subsystem |
| Reads vs writes | Split (multiple readers, exclusive writer) | Per-subsystem; writers in one don't block readers in another |

Apollo's single global lock means *every* read on the store serializes against *any* write. Cachebay's `Queries.lock` doesn't block `Fragments.lock`, neither blocks `Graph.lock` once `Graph.flush()` has dropped it.

### 4.2 The fanout window

This is the biggest single difference.

**Apollo** (`ApolloStore.swift:72–77`):

```swift
public func publish(records: RecordSet) async throws {
    try await readerWriterLock.write {
        let changedKeys = try await self.cache.merge(records: records)
        self.didChangeKeys(changedKeys)        // ← still inside the write block
    }
}
```

`didChangeKeys` (line 55–59) iterates every subscriber synchronously, calling `store(_:didChangeKeys:)` on each. Watchers spawn their own re-fetch `Task`s, but those tasks immediately try to take the *read* lock — which is queued behind the write lock that's still iterating.

**Cachebay** (`Runtime/Graph.swift`):

```swift
lock.lock()
let pending = drainPendingLocked()
lock.unlock()                  // ← lock released
onChange?(pending)              // ← fanout runs lock-free
```

`onChange` is the closure set in `CachebayClient.swift:161–181` that calls `Queries.notifyDataByDependencies(touched)` and `Fragments.notifyDataByDependencies(touched)`. Both run with no graph lock held; readers can race in.

Net effect: Apollo's mutation publish window scales with `(merge cost) + (watcher iteration cost) + (synchronous part of every subscriber callback)`. Cachebay's only includes `(merge cost)`.

### 4.3 Watcher refire

**Apollo** (`GraphQLQueryWatcher.swift:246`):

```swift
if !dependentKeys.isDisjoint(with: changedKeys) {
    guard let result = try await store.load(self.query) else { ... }
    self.dependentKeys = result.dependentKeys
    self.didReceiveResult(result)
}
```

`store.load` re-acquires the read lock, then runs `GraphQLExecutor.execute` over the full `SelectionSet`, fetching every record by key, materialising every nested struct. **Every refire is a full re-execute.** No memoization.

**Cachebay** (`Runtime/Queries.swift`):

```swift
let result = documents.materialize(
    plan: plan, variables: variables,
    options: .init(canonical: true, fingerprint: true,
                   preferCache: true, updateCache: false))
```

`Documents` keys cached materialised results by `(plan, variables, rootId)` fingerprint. Idempotent changes (a record was touched but the materialised data is structurally identical) skip the re-walk entirely.

### 4.4 Fanout indexing

Apollo iterates the watcher set per publish (`O(W × avg|dependentKeys|)`):

```swift
// GraphQLQueryWatcher.swift:246, called once per subscriber
if !dependentKeys.isDisjoint(with: changedKeys) { ... }
```

Cachebay maintains a reverse index (`Runtime/Queries.swift:51, 254–260`):

```swift
private var depIndex: [CacheKey: Set<Int>] = [:]   // record → watcher IDs

var affected: Set<Int> = []
for id in touched {
    if let set = depIndex[id] {
        affected.formUnion(set)
    }
}
```

`O(k)` where `k` = touched record count. Number of subscribers is no longer a per-publish cost.

### 4.5 SQLite write path

**Apollo's `SQLiteNormalizedCache.merge`** is synchronous SQLite I/O held inside the write lock. (Real production apps usually wrap it in a write-behind cache — itself a tell that this matters.)

**Cachebay's `SQLiteStorage.put`** (`Storage/SQLiteStorage.swift:36–52`):

```swift
private let queue = DispatchQueue(label: "cachebay.sqlite.storage", qos: .userInitiated)

public func put(_ records: ...) {
    if records.isEmpty { return }
    enqueueWork { [weak self] in
        self?.performPut(records)
    }
}
```

`put` returns immediately. Actual writes batch on a serial queue inside `BEGIN IMMEDIATE` / WAL / `synchronous=NORMAL`. Storage never holds any cache lock.

### 4.6 What is *not* different

A few things I told users were "the difference" before reading the source carefully — they aren't:

- **Reflection** — Apollo's read path is *not* reflection. It's compile-time-generated subscripts on `DataDict` (`DataDict.swift:94–104`):

  ```swift
  @inlinable public subscript<T: SelectionSetEntityValue>(_ key: String) -> T {
      get { T.init(_fieldData: _data[key]) }
  }
  ```

  `data.project.clips[0].id` is ~3–5 inlined subscripts. Cheap. Cachebay's `JSONValue` enum dispatch is in the same ballpark — possibly slightly slower per access, certainly not an order of magnitude.

- **Async/await hop overhead** — Apollo uses `actor` continuations; no DispatchQueue bridges. Each call costs a continuation suspend, not a thread hop. Cachebay synchronously holds locks but passes through actors via the transport layer. Wash.

- **Mutation publish unconditionality** — both publish on mutation success. Apollo can't opt out ([apollographql/apollo-ios#777](https://github.com/apollographql/apollo-ios/issues/777)); Cachebay also publishes. The cost difference is in *what publish does*, not whether it happens.

### 4.7 The honest performance summary

If your workload is "occasional mutation, watcher reads a small selection set," both clients perform fine. The differences kick in when:

1. **Mutations are frequent** — Apollo's lock-held-during-fanout serializes them; Cachebay's lock-released-before-fanout overlaps them.
2. **Watcher selection sets are heavy** — Apollo re-executes from scratch; Cachebay's fingerprint cache short-circuits unchanged subtrees.
3. **Many watchers per change** — Apollo iterates per watcher; Cachebay has an `O(k)` reverse index.
4. **SQLite is in the loop** — Apollo serializes through the cache lock; Cachebay decouples.

In a real-time editor (the workload that motivated this codebase), all four hit at once. Measured: 767 ms `MAIN-BLOCK` on Apollo became 27–39 ms full round-trip with no main-thread block on Cachebay, same workload, same network, same schema.

## 5) Known issues / engineering debt

This section is here because it's true, not because it's flattering. If you're evaluating Cachebay, read this; if you're contributing, work on this.

### 5.1 Fingerprint cache invalidation correctness is not provably sound

The materialize fingerprint cache is the second-largest perf win (§3). Its correctness depends on the registered dep set being *exactly* the records the materialised result depends on — no false negatives (stale UI), no false positives (defeats the cache).

There is no compiler-enforced contract that every record read inside `Documents.materialize` registers a dep. It's convention. A future code path that reads a record without registering it as a dep will silently break every watcher that depends on it.

**Fix:** property tests over the fingerprint cache. Generate random plans + random graph mutations; assert that watcher-observed results match the ground-truth re-execution. This is the single most impactful invariant to nail down.

### 5.2 Lock ordering is enforced by convention

The six-lock topology in §1 is documented in comments and *not* type-enforced. Any new code path that takes them in a different order can deadlock. As contributors come and go this gets harder to maintain.

**Fix:** phantom-typed lock guards or a token-passing API where you can only acquire `Graph.lock` if you can prove you hold a higher token. Significant API surface change but it's the principled answer.

### 5.3 `Graph.flush()` releases the lock — race window worth understanding

Releasing the lock before `onChange` is a feature. The trade-off: between the `unlock` and the consumer walking `touched`, *another writer can land more changes*. The current design handles this — `touched` is snapshotted under the lock — but consumers that read back the graph inside their callback can see a *newer* state than `touched` indicates.

This is documented in `Graph.swift` but easy to miss when writing watcher logic. Not a bug; a sharp edge.

### 5.4 Recursive locks are a code smell

`NSRecursiveLock` is used pervasively because watchers re-enter the same subsystem. It works. It's also widely considered an anti-pattern — recursive locks paper over architectural questions about who calls what, and they make accidental re-entry *easier*, not safer.

**Fix:** explicit "lock-free" APIs for the re-entrant paths. `Graph.getRecordLockFree(id:)` callable only with proof the caller holds a higher-tier lock.

### 5.5 `depIndex` bookkeeping under `WatchHandle.update(variables:)`

`watchQuery` registers dependent record IDs into `depIndex`. When `handle.update([…])` switches what the watcher observes, the dep index has to atomically remove the old entries and add new ones. This is exactly the kind of bookkeeping where one missed code path means watchers fire on wrong changes or fail to fire when they should.

**Fix:** property tests with shuffled `update(...)` calls; assert the steady-state dep set always equals the freshly-computed dep set.

### 5.6 Codegen lacks a representative-schema test suite

The CLI runs on a moderately complex schema (~40 ops, ~15 inputs, polymorphism, `@oneOf`, custom scalars, nested fragments, list-of-non-null variants, interface namespaces) end-to-end in production today. The bugs that surfaced during the early integration are fixed; the typed surface (operation conformance, accessor setters, fragment `onTypename` routing, `@oneOf` input encoding, schema interfaces map) has stabilised. What's still missing is the systematic test suite that would catch the *next* round of bugs before users do.

**Fix:** representative-schema codegen tests — cross-file fragments, polymorphism with 3+ branches, `@oneOf`, custom scalars, nested fragments, lists of various nullabilities, interface-rooted fragments routed through `canonicalTypename`. Generate, build, assert field-by-field semantic correctness against the same data round-tripped through the runtime.

### 5.7 `@unchecked Sendable` / `nonisolated(unsafe)` surface

Several spots in `CachebayClient.swift` and `Network/URLSessionWebSocketTransport.swift` use these escape hatches. Each is "I, the author, certify thread-safety." Load-bearing on author memory; TSan won't catch a future change that breaks an invariant.

**Fix:** audit each one, write a justification comment that captures the actual invariant, ideally pin it with a `precondition`.

### 5.8 Optimistic layer replay scales linearly

`Optimistic.commit / revert` restores baselines and replays surviving layers (`Optimistic.swift:159–201`). With *N* overlapping optimistic mutations queued, every commit replays *N − 1* others. Most apps don't hit this; a real-time editor with many in-flight optimistic edits could.

**Fix:** structural sharing — record which records each layer touches, replay only the affected subset. (May already be doing this; verify and document.)

### 5.9 WebSocket reconnection is implicit

`URLSessionWebSocketTransport` lazily opens one shared task. Explicit reconnect-with-backoff logic isn't visible. If the socket drops mid-session, the next `subscribe` re-opens; what happens to existing subscriptions during the gap is worth verifying with a network-disrupting integration test.

**Fix:** explicit reconnect state machine with backoff, observability hooks, and a documented contract for what subscribers see during a reconnect.

### 5.10 No middleware / interceptor chain

Auth is a `requestModifier` closure on `URLSessionHTTPTransport`. Want to add logging? Stack a closure. Retry? Stack another. There's no protocol-based composition like Apollo's `InterceptorProvider`.

For most apps this is fine. For pluggable observability, auth-rotation hooks, or per-request retry policy, you'll be wrapping the transport.

**Fix:** an interceptor protocol on `Transport` with a default chain. Backwards-compatible; closure-based auth becomes one default interceptor.

### 5.11 CachePlan literal size at startup

Every operation emits a static `CachePlan.make(…)` literal with `PlanField.make(…)` per field. For a large schema, that's substantial static-initialiser work at first access. Apollo's selection-array generation has the same characteristic; both can regress cold-start time on large schemas.

**Fix:** lazy plan construction (decode from a compact binary blob at first use). Likely not worth it until a real schema demonstrates the regression.

## 6) What's *not* a problem

For balance: things that look bold but are sound.

- **Lock-released-before-fanout** — primary perf win, well thought out.
- **Per-subsystem locks** — right granularity for the workload.
- **Fingerprint cache** — right primitive, even if the invariant needs hardening.
- **`depIndex` reverse index** — the right answer to Apollo's `O(W)` per-publish cost.
- **Async SQLite via serial queue** — never blocks the cache lock.
- **Compile-time `CachePlan`** — runtime never parses GraphQL.
- **Typed cache mutation API** — `client.readFragment<F> / writeFragment<F> / watchFragment<F>` keyed by bare entity id; `b.patch(fragment: F.self, id:) { … }` closure-builder writes only touched fields; `c.linkNode(node: N, options:)` / `c.unlinkNode(fragment: F.self, id:)` for connections. Variant-rooted fragments route via `Graph.canonicalTypename` so they land on the canonical interface key. See [CODEGEN.md](./CODEGEN.md), [FRAGMENTS.md](./FRAGMENTS.md), [OPTIMISTIC_UPDATES.md](./OPTIMISTIC_UPDATES.md).

These are the load-bearing decisions. They're the reason Cachebay outperforms Apollo on the workload that exposed it.

---

## 7) Bottom line

Cachebay's architecture solves real perf problems that Apollo iOS 2.x has on real workloads. The wins are concrete, measurable, and architectural (not micro-optimisations). The debt is real too: invariants enforced by convention, codegen test coverage that hasn't caught up to the runtime surface, a few escape-hatch annotations that need pinning. None of it is unfixable; all of it is engineering that hasn't been done yet.

If you're shipping a high-edit-rate iOS app on Apollo and feeling the lock contention, switch. If you're shipping a low-edit-rate CRUD app and Apollo works, the migration cost probably outweighs the ergonomic differences.

Either way, the real reason to read this doc is to know what you're standing on.
