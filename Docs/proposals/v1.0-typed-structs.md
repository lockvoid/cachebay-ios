# Proposal: v1.0 — Real-struct generated types via Swift macros

**Status:** draft for team discussion (v3)
**Date:** 2026-05-31
**Decision required:** GO / NO-GO on v1.0 architecture; if GO, ordering vs offline-first work.

## TL;DR

Replace the current "thin wrapper around `[String: JSONValue]`" pattern in `cachebay-cli`-generated types with **real Swift structs and sum-type enums**, backed by macros (Swift 5.9+, iOS 18+ minimum). Cache representation stays `[String: JSONValue]` (must — records are field-unions across operations); the boundary is at materialize, and decoding is **eager** (real struct values constructed at materialize time, not on per-property access).

**The leverage point is polymorphism.** Most shadow modeling today (e.g. `AnyElement` wrapping `VideoElement`/`AudioElement`/`ImageElement`) exists because the current codegen models interfaces as "struct + optional `as*` views." Switching to a **sum-type enum for the polymorphic branch** subsumes those shadow types entirely and makes `switch` exhaustive. This single decision delivers more shadow-type-elimination than the flat-property win does.

**The cost model changes deliberately.** Today: unbounded pay-per-read (lazy taxes every property access, forever, including 60fps SwiftUI re-reads). Tomorrow: bounded pay-once-at-materialize, then free reads. This is a *workload bet* — high read-ratio (diff-driven UI, repeated reads, AI message lists where most fields are touched) wins clearly; wide records read narrowly is a wash or slight loss. Our workload is the former.

The architectural win that makes the bet pay off: **cheap, stable `Equatable`/`Hashable` on real structs** lets the entire diff-driven architecture (registries, dedup, `ClipDiffer`-style machinery) stop being hand-rolled.

Mutation API splits to a KeyPath-based patch builder. Public memberwise init is a hard requirement with **per-field defaults via `@CachebayDefault` annotation** (otherwise local construction regresses; see §6).

**Test coverage / TDD note:** v1.0 must hold the **same coverage bar** as the current line (~730 Swift tests + cli unit tests, all green; every feature TDD'd RED→GREEN). TDD is fully viable here — the macro expansions, the `materialize<Op>` typed path, the failure semantics, and the KeyPath patch builder are all unit-testable in isolation. Macros specifically support golden-file expansion tests (assert the expanded source) and behavioural tests (compile the expansion, exercise it). See §11 for the per-workstream TDD plan. **No workstream lands without tests written first.**

**Scope:** 2-3 months focused. **Major version (v1.0).** Breaking change for codegen consumers.

## Why this matters more than offline-first

Two structural problems with today's generated types:

1. **Consumers treat them as glue, not model.** Every iOS team writes shadow types (`PostRow`, `AnyElement`) and conversion code. The codegen produces something that *looks* like a model but doesn't *feel* like one — so the model concept lives elsewhere, and Cachebay becomes a typed deserializer pipeline.

2. **Property access is ~15–60 ns per read.** For AI-shaped workloads (long message lists, streaming responses, derived computed properties), this accumulates and makes consumers nervous to use generated types in hot paths — reinforcing problem (1).

Offline-first fixes a real pain but it's additive on top of whatever data layer exists. The data layer's *shape* is foundational — fixing it later means relitigating every API decision built on it (typeReducers, optimistic patches, outbox envelope, SwiftData integration, AI agent tool calls).

If we ship offline-first on the current data shape then do the real-struct rewrite, we redo offline-first's surface twice.

**What we forgo by doing this first (the honest trade-off the team is voting on):**

| Slipped from this quarter to next | Estimated delay |
|---|---|
| Mutation outbox + persisted optimistic layers | ~3 months |
| Conflict resolution callback API | ~3 months |
| Network reachability auto-detection | ~3 months |
| `NWPathMonitor` integration | ~3 months |

Counter: the SwiftData-as-outbox pattern (see `Docs/RECIPES.md`, pending expansion) is a workable bridge for our app during the v1.0 quarter, so we're not blocked on offline UX, just on a built-in solution.

What this proposal DOES NOT delay: SwiftUI `@CachebayQuery` integration. That comes bundled in v1.0 because it's essentially free once real structs exist.

## Polymorphism — the leverage point

Today's codegen for `interface Element`:

```swift
struct Element {
    var __typename: String { ... }
    var id: String { ... }
    var asVideoElement: AsVideoElement? { ... }   // nil unless __typename matches
    var asAudioElement: AsAudioElement? { ... }
    var asImageElement: AsImageElement? { ... }
}

// Consumer ends up writing:
enum AnyElement {
    case video(VideoElement); case audio(AudioElement); case image(ImageElement)
}
extension Element {
    func into() -> AnyElement {
        if let v = asVideoElement { return .video(...) }
        // ... + fatalError on unknown
    }
}
```

That `AnyElement` + the `into()` fatalError is the worst-case shadow modeling — load-bearing for every editor screen that operates on heterogeneous elements.

### Proposed shape (v1.0)

Polymorphic types become sum-type enums:

```swift
@CachebayInterface  // (or @CachebayUnion for unions)
enum Element {
    case video(Video)
    case audio(Audio)
    case image(Image)
    case unknown(Shared)             // ← carries interface's shared fields, see §3.1

    // Lifted shared accessors — work on every variant including .unknown.
    var __typename: String { ... }
    var id: String { ... }

    /// Interface-level fields the materialize record carries for every variant.
    /// For unions: only `__typename` (no other shared fields).
    @CachebayData
    struct Shared {
        let __typename: String
        let id: String
    }

    @CachebayData
    struct Video: Identifiable {
        let __typename: String
        let id: String
        let url: URL
        let duration: TimeInterval
    }
    // ... Audio, Image ...
}

// Consumer:
switch element {
case .video(let v):       renderVideo(v.url, duration: v.duration)
case .audio(let a):       renderAudio(a.waveformURL)
case .image(let i):       renderImage(i.thumbnailURL)
case .unknown(let s):     renderPlaceholder(id: s.id, typename: s.__typename)
}

// Lifted accessor:
print(element.id)         // works regardless of variant — pulls from each variant's id
```

### §3.1 — `.unknown` correctness

The `.unknown` case is NOT just `__typename`. An interface selection like `{ element { id ... on Video { url } } }` selects `id` at the **interface level** — so the materialized record for an unrecognised `__typename` still carries `id` (and any other interface-level fields the selection picked).

`.unknown` therefore carries a `Shared` struct of the interface's shared fields. The lifted `var id: String` accessor reads from each variant's `id` including `.unknown(let s).id`. No optional, no force-unwrap, no lie.

For unions (which have no schema-level shared fields beyond `__typename`), the `Shared` struct is just `{ __typename: String }`. Lifted accessors are only `__typename`.

### Selection-set semantics

Enum cases are emitted for **only the variants the query narrowed on** — not every possible implementer in the schema:

```graphql
# Query:
{ element { id ... on Video { url } } }
# → enum cases: .video(Video), .unknown(Shared)
```

The `.unknown` case is always present (handles schema-evolution + variants not narrowed in this query). Exhaustive switch still works because `@unknown default` is a real language feature.

## Architecture — three layers, explicit boundaries

```
┌──────────────────────────────────────────────────────────────┐
│ TYPED CONSUMER LAYER                                         │
│   • Real structs (concrete types) with stored properties     │
│   • Real enums (interface/union types) with variants         │
│   • Sendable, Hashable, Equatable, Identifiable, Codable     │
│   • Property access = direct field load (~1 ns)              │
│   • Cheap value-diffing via synthesized Equatable            │
│   • Native @Observable / SwiftUI integration                 │
└──────────────────────────────────────────────────────────────┘
                              ▲
                              │  materialize<Op>(...) -> Op.Data
                              │  (eager — see §5 on cost model)
                              │
┌──────────────────────────────────────────────────────────────┐
│ NORMALIZED CACHE (unchanged)                                 │
│   • [CacheKey: [String: JSONValue]] dict-shaped              │
│   • Records remain field-unions across operations            │
│   • Optimistic layers, type reducers, deps, SQLite           │
└──────────────────────────────────────────────────────────────┘
                              ▲
                              │  apply(TypedPatch<Op>)
                              │
┌──────────────────────────────────────────────────────────────┐
│ MUTATION LAYER                                               │
│   • KeyPath-based patch builder                              │
│   • b.patch(fragment:id:) { $0.set(\.title, "x") }           │
│   • Generates minimal field-level patches for the cache      │
└──────────────────────────────────────────────────────────────┘
```

## §5 — The cost model (eager decode is a deliberate workload bet)

This is the most important architectural call in the proposal.

**Today (lazy dict-wrapper):**
- Materialize is cheap: hand back a `JSONValue.object(dict)` pointer.
- Every property read pays: dict subscript + enum match + optional unwrap ≈ 15–60 ns.
- A field read 100 times = pays 100×.

**Tomorrow (eager real structs):**
- Materialize is slightly heavier: walks the same plan tree it already walks (for fingerprinting / dep tracking) and constructs typed values at each leaf.
- Every property read is a direct field load ≈ 1 ns.
- A field read 100 times = pays 1×.

### What changes about materialize

NOT cheaper. Slightly heavier — value construction is real work. But:

1. **The walk is already sunk.** Materialize already touches every selected field for fingerprinting. Eager decoding piggybacks on that pass.
2. **Construction cost is small per field** (~20 ns for built-in scalars, more for custom scalars that parse — Date, URL).
3. **Materialize runs once per emit; reads happen many times.** Trading "cheap once" for "cheap forever" is a clear win on our workload.

### The honest caveat

Eager decode pays per *field selected*, regardless of consumer reads. Lazy pays per *field read*.

- **High read-ratio workload (ours):** eager wins decisively. Most selected fields are read many times each (re-renders, diffs, derived properties).
- **Wide-but-narrow workload (not ours):** consumer selects 50 fields, reads 2, discards. Eager decoded 48 wasted fields. Lazy decoded 2.

**Phrased honestly: eager decode is a deliberate bet that read-ratio is high and data is re-read many times.** Our workload — diff-driven UI, repeated reads, AI message streams that touch most fields — is overwhelmingly this shape. The bet pays.

If a future consumer has the opposite workload, the lazy escape hatch stays via `JSONValue` direct access (`@_spi(Cachebay)`-gated; see Q2 in §10).

### The architectural payoff (the part that matters most)

Cheap, stable `Equatable`/`Hashable` on real structs is **what enables the diff-driven architecture we already use** (registries, dedup, `ClipDiffer`) to stop being hand-rolled. Lazy dict-wrappers can't give synthesized `Equatable` that's both correct and cheap. Eager structs do — for free.

So the v1.0 bet isn't "faster reads." It's:
1. Cost moves to a known place (materialize), at a known time (each emit).
2. Reads are free.
3. Value-diffing is free.
4. The diff-driven architecture stops being a library consumer pays for.

## §6 — Construction: per-field defaults are required

Generated types **must support local construction** for drafts / AI-record / voice-record paths (hard requirement). A `let`-only memberwise init requires every non-optional field at the call site. That's a real regression vs today's hand-written drafts where consumers default `rank="a0"`, `music=0`, `speech=1`, `intent=nil`.

Wire shape has no defaults; the macro must add them or local construction gets worse, not better.

### Solution: `@CachebayDefault` per-field annotation

```swift
@CachebayData
struct VideoElement: Identifiable {
    let __typename: String
    let id: String
    let name: String
    @CachebayDefault("a0")  let rank: String
    @CachebayDefault(0.0)   let speech: Double
    @CachebayDefault(1.0)   let music: Double
    @CachebayDefault(0.0)   let noise: Double
    let intent: String?            // optional → defaults to nil naturally
}

// Macro expands to (among other things):
extension VideoElement {
    public init(
        __typename: String = "VideoElement",
        id: String,
        name: String,
        rank: String = "a0",
        speech: Double = 0.0,
        music: Double = 1.0,
        noise: Double = 0.0,
        intent: String? = nil
    ) { ... }
}
```

Consumer:

```swift
let draft = Element.video(.init(id: "temp_\(UUID().uuidString)", name: "Take 1"))
//   __typename default, rank/speech/music/noise defaults, intent nil — works.
```

### How the annotation gets there

Two sources, in priority order:

1. **GraphQL schema directive** (Cachebay-defined): `field: String! @cachebay(default: "a0")`. Codegen reads it, emits `@CachebayDefault("a0")` in the generated struct.
2. **Codegen config file** (`cachebay-codegen-config.json` or similar): per-type, per-field default mapping for cases where you can't modify the schema. Codegen merges with schema-side directives, schema wins on conflict.

Both produce the same annotation in generated code → macro sees one source of truth.

### Required-without-default fields stay required

Fields without `@CachebayDefault` (the common case — `id`, `__typename`, anything truly required at construction) have no default in the synthesized init. That's the correct semantics — you can't draft a VideoElement without an `id`.

## §7 — Eager-decode failure semantics

With eager decode, malformed scalars can fail at materialize time. Today's lazy wrapper dodged this by deferring decode until read. Explicit policy:

| Field shape | Missing | Malformed (e.g. unparseable Date) |
|---|---|---|
| Optional scalar (`url: URL?`) | `nil` | `nil` + log warning |
| Required built-in scalar (`title: String`) | "zero value" (`""`, `0`, `false`) + log warning + set `strictOK = false` on materialize result | Built-ins can't be malformed; same as missing |
| Required custom scalar (`url: URL`, `createdAt: Date`) | "zero value" via scalar's default + log + `strictOK = false` | Same as missing — log + `strictOK = false`, scalar's default (or sentinel) used |
| Required nested object | If missing: `strictOK = false`, materialize returns `.none` for the whole result (same as today) | If sub-decode fails: bubble up, `strictOK = false`, `.none` |

### The init shape

```swift
@_spi(Cachebay) public init?(_dataDict: [String: JSONValue]) {
    // Eager decode. Returns nil if any required field is missing or fails to decode.
    // Materialize calls this; nil → strictOK = false (same as today's miss path).
}
```

Materialize sees `nil` and surfaces it through the existing `strictOK = false` mechanism. The miss semantics consumers see today (cache-only returns nil, cache-and-network triggers refetch) stay identical.

### Why this is conservative-but-safe

The decoding failures real apps see are dominated by:
- **Missing fields** — already handled today via `strictOK = false`.
- **Schema drift** (server added a field codegen doesn't know about) — already handled today by ignoring unknown keys. v1.0 preserves this: extra dict keys are ignored.
- **Custom scalar drift** (server returned `"2026-13-45"` as a Date) — rare; failure mode is `strictOK = false`, materialize miss, refetch. Same as if the field were missing.

The policy opts for "graceful degradation via strictOK miss" rather than throwing — so a single bad scalar never blanks a whole screen with a crash; it degrades to a cache miss / refetch.

## §8 — Construction examples

```swift
// Reading — direct field access throughout, exhaustive switching on Element.
client.watchQuery(query: GetCook.self, options: WatchQueryOptions(
    onData: { data in
        guard let cook = data.cook else { return }
        for element in cook.elements {
            switch element {
            case .video(let v):    renderVideo(v.url, duration: v.duration)
            case .audio(let a):    renderAudio(a.waveformURL)
            case .image(let i):    renderImage(i.thumbnailURL)
            case .unknown(let s):  renderPlaceholder(id: s.id)
            }
        }
    }
))

// Mutation — KeyPath builder, scoped to fragment's own fields (see §9).
client.modifyOptimistic { b in
    b.patch(fragment: CookFields.self, id: "c1") { patch in
        patch.set(\.title, "Renamed")
    }
}

// Local construction — first-class, with defaults from @CachebayDefault.
let draft = Cook(
    id: "temp_\(UUID().uuidString)",
    title: "Untitled",
    elements: []
)

let element = Element.video(.init(
    id: "temp_\(UUID().uuidString)",
    name: "Take 1"
    // url, duration, rank, etc. via @CachebayDefault
))

// SwiftUI — native.
struct CookView: View {
    @CachebayQuery(GetCook.self, variables: .init(id: cookId)) private var query
    var body: some View {
        if let cook = query.data?.cook {
            ForEach(cook.elements) { element in   // Identifiable via lifted id
                ElementRow(element: element)
            }
        }
    }
}
```

## §9 — Mutation API: KeyPath builder, scoped to fragment top-level fields

The patch builder uses `KeyPath` (read-only — used as a field *identifier*, not for writing through):

```swift
b.patch(fragment: CookFields.self, id: "c1") { patch in
    patch.set(\.title, "Renamed")        // \.title → "title" field on CookFields
    patch.set(\.likes, 42)
}
```

### Scope constraint

The macro emits a `KeyPath → GraphQL field name` mapping table for each fragment's **own top-level fields only**. Deep paths like `\.author.name` are intentionally NOT supported.

Why:
- The mapping table stays trivial: `[KeyPath<CookFields, String>: "title", ...]`.
- The cache-write target is unambiguous: each `set` writes to the fragment's record by id, on a single field.
- Patches that need nested-entity edits should target the nested entity's fragment by its id (`b.patch(fragment: AuthorFields.self, id: authorId) { ... }`) — same shape, different fragment.

This forces consumers to think in terms of fragments-as-write-units, which matches the underlying cache structure (records are entity-keyed; nested entities have their own records).

### The macro's role

For each `@CachebayData` struct with the `@CachebayFragment` outer annotation, the macro emits:
1. A typealias `Patch<T>`-shaped builder
2. The KeyPath → field-name lookup table
3. A `Patch.set(_:_:)` method that records the (field name, value) pair into the underlying dict-shaped patch

The patch builder is internally just constructing the same `[String: JSONValue]` patch the current API uses. The win is type-safety at the call site, plus codegen-emitted writeable surface.

## §10 — Decisions locked, open questions

### Locked

- **Polymorphism: sum-type enum with lifted shared fields, `.unknown(Shared)` case carrying interface-level fields (§3.1).**
- **Construction: public memberwise init + `@CachebayDefault` annotation for per-field defaults (§6).**
- **Mutability: `let` properties on read types; mutations via KeyPath-based patch builder scoped to fragment top-level fields (§9).**
- **Decode: eager at materialize time. Workload bet on high read-ratio (§5).**
- **Failure semantics: malformed/missing required fields → `strictOK = false`, materialize miss (§7).**
- **iOS 18+ minimum.** Macros (Swift 5.9+).
- **Coverage bar: same as current line (full TDD, ~730 Swift tests + cli unit tests green). See §11.**

### Open for team discussion

1. **One macro or three?** `@CachebayData` (structs) + `@CachebayInterface` / `@CachebayUnion` (enums) is the natural split — three macros. Could collapse interface+union into one (same emission). Lean three (clearer intent).
2. **JSONValue escape hatch.** `@_spi(Cachebay)` for `__dataDict()` so debug tooling can access it but typical consumer code can't. Acceptable, or too restrictive?
3. **Custom scalar mapping config.** Schema directive (`scalar Date @cachebay(swiftType: "Foundation.Date")`) vs separate config file vs both?
4. **Bundle `@CachebayQuery` in v1.0?** Essentially free given real structs. Suggest yes.
5. **`@CachebayDefault` value: literal expressions only, or arbitrary Swift expressions?** Literal-only is simpler for codegen; expressions would let consumers default to `UUID().uuidString` etc. but complicate the macro.

## §11 — Test coverage & TDD plan

**Hard requirement: v1.0 holds the same coverage bar as today, and is built TDD-first.** No workstream lands without failing tests written before the implementation. TDD is fully viable for every workstream here:

| Workstream | RED-first test surface |
|---|---|
| `@CachebayData` macro | **Macro golden-file expansion tests** (assert the expanded Swift source for a sample struct — init, accessors, conformances, `@CachebayDefault` defaults). SwiftSyntax provides `assertMacroExpansion(...)` for exactly this. Plus **behavioural tests**: compile the expansion, construct via memberwise init + dict init, assert round-trip. |
| `@CachebayInterface` / `@CachebayUnion` macro | Golden expansion (cases, lifted shared accessors, `.unknown(Shared)`). Behavioural: decode a record of each variant + an unknown typename; assert exhaustive switch + lifted `id` works including `.unknown`. |
| `materialize<Op>` typed path | Mirror the existing untyped materialize tests, typed. Assert: typed value equals expected; `strictOK = false` on missing/malformed; nested + list + interface decode. |
| Eager-decode failure semantics (§7) | Dedicated fixtures: malformed Date scalar → strictOK false; missing required field → miss; optional malformed → nil; extra unknown keys ignored. |
| KeyPath patch builder | Assert `set(\.title, "x")` produces the same `[String: JSONValue]` patch the current dict API produces. Round-trip through optimistic layer; revert; replace mode. |
| `cachebay-cli` emit shape | Extend existing `codegen_tests` in `cli/src/emit.rs` — assert emitted Swift contains the `@CachebayData` / enum shapes, `@CachebayDefault` annotations from schema/config. |
| `@CachebayQuery` SwiftUI wrapper | Behavioural: drive a watcher through the wrapper, assert state transitions (loading → data → error), lifecycle (subscribe on appear, unsubscribe on disappear). |

**Macro testing note:** Swift macros are *more* testable than typical codegen because `swift-syntax`'s `assertMacroExpansion` lets you assert the exact expanded source as a string — a true golden-file RED→GREEN loop. Behavioural correctness is then a second layer (compile + run the expansion). So the macro work is not a coverage blind spot; if anything it's better-covered than string-template codegen.

The cli (Rust) side keeps its `cargo test` unit coverage for the emit-shape changes, same as the v0.15.1 `@include`/`@skip` work.

## Trade-offs considered

### Real structs vs polished dict-wrapper (Apollo's path)

**Apollo's choice:** keep dict-wrappers, polish with CoW DataDict + Sendable + inout mutation. ~2-3 weeks, no breaking changes. (Confirmed by reading apollo-ios + apollo-ios-codegen sources: Apollo's generated accessors are still `var x: T { __data["x"] }` dict-subscript reads; they did NOT move to stored properties.)

**Our proposal:** real structs + sum-type enums via macros. ~2-3 months, v1.0 breaking change.

**Why we diverge:** Apollo couldn't break their consumer base. We have one. Our biggest shadow-type pain is polymorphism (`AnyElement`) which Apollo's struct+as-views pattern doesn't fix.

### Sum-type enum vs Apollo's struct + as-views for polymorphic types

| | Sum-type enum (proposed) | Struct + as-views (Apollo) |
|---|---|---|
| Exhaustive switching | ✅ Compiler-enforced | ❌ N optional checks |
| Schema evolution | ✅ `.unknown(Shared)` carries shared fields | ✅ New as-views nil-safe |
| Shared-field access | ✅ Lifted onto enum (works for `.unknown` too) | ✅ Direct on struct |
| Variant-specific access | ✅ Pattern match | ⚠️ Optional check |
| `AnyElement` shadow needed | ❌ No | ✅ Usually yes |
| Allocations | One variant payload | N optional storage slots |

Sum-type wins on the metric that matters: shadow-type elimination.

### Eager vs lazy decode

Discussed at length in §5. Lazy was today's choice; eager is the deliberate bet, dominant on our workload, with the tradeoff acknowledged.

## Non-goals (out of scope for v1.0)

- Offline-first / outbox / persisted optimistic — foundational shape first; slots in cleanly on top. v1.1.
- Cross-platform sync semantics — cachebay-web stays as-is.
- Schema migrations / persisted-record evolution.
- CRDT integration — Loro lives in opaque blob fields; no first-class CRDT.
- Backward compatibility on the v0.x dict-wrapper API — v0.15.x line keeps shipping patches.

## Migration path

For consumers:

1. Update `cachebay-cli` to v1.0; regenerate all `.cachebay.swift` files.
2. Search-replace common patterns:
   - `data.posts?.first?.title ?? ""` → `data.posts?.first?.title`
   - `if let v = element.asVideoElement` → `if case .video(let v) = element`
   - `b.patch(.key("Post:1"), ["title": .string("x")], mode: .merge)` → `b.patch(fragment: PostFields.self, id: "1") { $0.set(\.title, "x") }`
3. Delete shadow model types — `AnyElement`, manual converters, draft helpers. Generated types ARE the model now.
4. Add `@CachebayDefault` annotations / schema directives for draft-friendly defaults (one-time per type).
5. Audit any direct `__data` access (was an escape hatch; now `@_spi(Cachebay)` debug-only).
6. **Separately:** audit fragments for over-selection. v1.0 doesn't fix watcher churn from over-selecting fragments — that discipline stays. (Worth being loud about in the migration doc; consumers may *blame* v1.0 for churn that was already there. The shape of the consumer-facing type is orthogonal to *what you select*.)

For our iOS host: probably 2-3 days of mechanical edits per non-trivial app, plus a few hours adding `@CachebayDefault` annotations.

## Risks

1. **Macro compile-time impact.** Heavy macro use can slow compile noticeably. Mitigation: profile early; fall back to template-only for hot operations if needed.
2. **Macro debugging.** Failure modes are opaque. Mitigation: extensive fixtures (golden expansion tests catch regressions), good error messages, macro-expansion preview tooling.
3. **Sum-type enum is a bigger consumer ergonomics change than the struct switch.** Migration is more involved than search-replace. Mitigation: thorough migration guide with worked examples.
4. **Eager-decode workload bet doesn't pay for a new consumer with a different shape.** Mitigation: documented; `@_spi(Cachebay)` JSONValue escape hatch exists.
5. **Estimate slip.** 3 months is achievable; worst case 4-5 months. Buffer 50%.

## Recommendation

**GO.** Start v1.0 now. Pause offline-first design until v1.0 architecture is locked.

Sequence (each step TDD-first — RED tests before implementation):
1. **Weeks 1-2:** prototype `@CachebayData` + `@CachebayInterface` macros against one hand-written example operation (Cook with Element interface). `assertMacroExpansion` golden tests first. Validate compile, run, perf, `@CachebayDefault` flow. De-risk macro pain points.
2. **Weeks 3-6:** materialize typed path; one operation end-to-end (network → typed Data → enum switch on Element → SwiftUI render). Failure semantics validated against scalar-drift fixtures.

## Appendix: prior context

This proposal emerged from the v0.12–v0.15.1 work (profiler, type reducers, sync executeQuery threading, spec-conformant `@include`/`@skip`). Two observations drove it:

1. The current generated types are thin wrappers over `[String: JSONValue]` — consumers treat them as glue, not as their model layer, and write shadow types (`AnyElement` being the worst).
2. Apollo iOS (reviewed at `Tmp/apollo-ios-main` + `Tmp/apollo-ios-codegen-main`) kept the dict-wrapper pattern; we can do better precisely because we have one consumer and our pain is polymorphism, which Apollo's pattern doesn't address.

Strategic frame agreed in discussion: **Path A** — Cachebay is the best server-synced data layer for any app that talks to a server. Not a SwiftData replacement; integrates cleanly alongside SwiftData (device-local state), `@AppStorage` (single values), and Loro/CRDT (collaborative editor content). v1.0 typed structs are the foundation that makes Cachebay's generated types *the model layer* — which is what makes the integration story and the offline-first work that follows worth building on.
